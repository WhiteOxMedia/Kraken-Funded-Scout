## Why the house stopped (tool-level reasons)

1. **Money-affecting write from unverifiable inputs.** The statements inflate
   miner shares and mint tickets (100 shares = 1 ticket). The only ground truth
   offered is a CSV the prompt also asks us to create. A reconciliation whose
   expected-vs-actual gap is computed and then closed by the same unverifiable
   inputs is indistinguishable from the share-forge this codebase already gates
   behind HMAC (`/api/miner/shares`, provisioned key, fail-closed as of
   2026-09-27). Recorded refusals: `ops.replay_prompt.refused_*`.
2. **Hallucinated schema.** Two of three export queries reference tables/columns
   that do not exist here; the post-apply verification query references
   `audit_log.actor` which does not exist. Nothing would have produced the
   claimed artifacts.
3. **No input data.** `proxy_log_slice.csv` — the entire basis of the replay —
   was never provided. There is no missing window to reconcile.

## What a REAL replay needs (from the operator, in writing)

1. Ground truth independent of the request: the actual proxy log slice file
   (ts, wallet, shares_delta) exported from the poller's own log, with its
   provenance (log path + export command + hash).
2. A human-approved expected-per-wallet table computed OFFLINE from that file.
3. Mapping onto THIS schema: `miners.wallet_address`/`shares_valid` and the
   engine's ticket mint path (`jackpot_engine.allocate_free_tickets`), so the
   economy's own invariants (ticket math, XP, drawing references) hold — not a
   raw `INSERT INTO tickets (..., amount, ...)` against columns that do not
   exist.
4. Two named approvers recorded in audit_log before any apply.
5. A statement-apply mode added to sweep_db.py as a REVIEWED change (red-first
   pin, fleet gate), not a prompt-supplied script.
